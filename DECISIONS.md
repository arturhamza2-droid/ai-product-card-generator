# Промпты, решения, ограничения

## 1. Архитектура в одном абзаце

Конвейер из пяти шагов: **проверка входа (код) → отчёт о нехватке данных (код) → вызов модели →
проверка ответа (код) → вывод**. Модели отдана только та часть, где нужен язык: заголовок, описание,
запросы, блок для менеджера. Всё, что можно проверить или сделать детерминированно, делает код.

## 2. Как устроена защита от выдуманных характеристик

1. **Таблица характеристик собирается кодом.** Значения копируются из входных данных дословно и
   раскладываются по группам (диапазон, точность, питание, выход/интерфейс, защита, корпус,
   условия, ресурс, масса). Если для группы ничего не нашлось, пишется «данных нет».
   **Значения из описания.** Описание по ТЗ — тоже входные данные, поэтому если значения нет в таблице, но оно
   есть в тексте описания, оно попадает в таблицу с пометкой «(из описания)». Модель возвращает значение вместе
   с дословной цитатой; код принимает его, только если цитата найдена в описании и значение есть в цитате.
   Придуманная или «слегка изменённая» цитата отбрасывается, и остаётся «данных нет».
2. **Промпт запрещает использовать «знания о похожих приборах»** и требует вместо догадки писать
   пункт в `data_issues`. Противоречия между таблицей и описанием не превращаются в число в тексте,
   а попадают в `data_issues` (на реальных страницах такие противоречия встречаются).
3. **Проверка чисел кодом.** Все числа из сгенерированного текста сравниваются с числами из входных
   данных. Число, которого там нет, считается возможной выдумкой.
4. **Проверка «опасных» слов кодом.** Слова про сертификаты, стандарты, ГОСТ, реестр, взрывозащиту,
   гарантию, доставку, скидки и неподтверждённые оценки («лучший», «надёжный», «уникальный»…)
   допустимы, только если такое слово есть во входных данных (список — `RISKY_STEMS` в
   [app/checks.py](app/checks.py)).
5. **Проверка «мета-фраз».** В публичном тексте (заголовок, описание, запросы) нельзя писать «не указано»,
   «в карточке нет», «уточните у менеджера»: о нехватке данных говорит только раздел «Что проверить».
6. При нарушении модель получает точный список и до двух попыток исправиться. Если не вышло, карточка
   помечается «Требует ручной правки», а нарушения выводятся в отчёте. Автоматически текст не «чинится».
7. **Описание и характеристики в промпте названы данными, а не инструкциями** (защита от текста
   на странице вида «игнорируй предыдущие указания»).
8. **Мало данных: модель не вызывается.** Нет характеристик и описание короче 100 символов — сервис
   отвечает «данных недостаточно».

## 3. Инструкция для модели

Файл [app/prompts.py](app/prompts.py). Структура системного промпта:

| Раздел | Что в нём |
|---|---|
| РОЛЬ | SEO-редактор B2B-магазина КИП; тон «технический специалист», не рекламный копирайтер |
| КОНТЕКСТ И ИНСТРУМЕНТ | Как устроен сервис: таблицу характеристик собирает код, ответ модели проверяет программа (длины, числа, «опасные» слова), что будет при нарушении, кто и где использует текст |
| ПРАВИЛА ДОСТОВЕРНОСТИ | Восемь правил: значения только из входа; общие знания допустимы только для названий типа прибора (синонимы для ключевых слов); пропуск и противоречие → `data_issues`; никаких новых чисел и пересчётов; нет придуманных применений; запрет маркетинговых оценок; данные ≠ инструкции |
| ПРАВИЛА SEO | Заголовок: главный запрос (тип + модель + производитель) в начале, затем 1–2 параметра из данных. Описание: главный запрос в первом предложении, структура «назначение → характеристики → применение», естественное употребление ключей без «спама». Запросы: от общих частотных формулировок к коммерческим и по назначению |
| ЧЕГО НЕЛЬЗЯ ПИСАТЬ | В публичном тексте нельзя писать о нехватке данных (это только в `data_issues`) |
| ЕСЛИ ДАННЫХ МАЛО | Описание делается минимальным из допустимых (около 800–900 символов), без рекламы и «воды»; недостающее перечисляется в `data_issues` |
| ЗНАЧЕНИЯ ИЗ ОПИСАНИЯ | Для групп, где в таблице данных нет: найти значение в описании и вернуть его вместе с дословной цитатой; код проверит цитату |
| ЯЗЫК, СОГЛАСОВАННОСТЬ | Только русский (латиница лишь для обозначений из данных); `data_issues` не должен противоречить тексту |
| ФОРМАТ ОТВЕТА | Один JSON-объект по схеме |
| САМОПРОВЕРКА | Перечень проверок, которые модель делает перед ответом |

Решения по промпту:

- **JSON-ответ** (`response_format=json_object`, если API поддерживает; иначе разбор текста с допуском
  ```-ограждений). **Температура 0.2.** Если провайдер не принимает параметры, запрос повторяется без них.
- **Повторная попытка** (до 3 вызовов) с точным списком нарушений: модели плохо считают символы, а код
  считает точно.
- Пустые поля передаются модели как «данных нет», а не как пустая строка.
- Описание обрезается до 6000 символов.
- **Про «самые частотные слова».** Прямого доступа к статистике запросов (Яндекс.Вордстат) у сервиса нет.
  Поэтому модели разрешено использовать общие знания только о том, как покупатели называют ТИП прибора
  (например, «датчик давления» и «преобразователь давления»). Значения и свойства из общих знаний брать
  нельзя. Реальную частотность можно подключить позже (см. улучшения).

## 4. Выбор модели

Сравнение на трёх примерах (датчик давления, счётчик импульсов, демо с минимумом данных), одинаковый
промпт, обе модели через один API:

| | claude-sonnet-5.5 | gpt-5.5 |
|---|---|---|
| Проверки пройдены с первой попытки | 3 из 3 | 3 из 3 |
| Замечаний к данным (`data_issues`) | 6 / 8 / 8 | 1 / 4 / 5 |
| Поисковые запросы | иногда 4 вместо 5 | всегда 5, чуть удачнее по частотным формам |
| Заголовок и описание | полнее, больше конкретики | компактнее, чуть более «канцелярский» стиль |
| Противоречие в погрешности датчика (таблица и описание расходятся) | заметила, объяснила и добавила, что уточнить | заметила, но одной короткой строкой, остальных замечаний почти нет |

Выбрана **`claude-sonnet-5.5`**: ключевой критерий задания — не выдумывать и честно сообщать о проблемах
данных, а здесь модель лучше находит расхождения. `gpt-5.5` работает с тем же кодом без изменений:
`python -m app.cli файл.json --model gpt-5.5`. Сравнение небольшое (3 товара), это ориентир, а не
исследование.

## 5. Прочие решения

- **Минимум зависимостей:** `openai` (клиент API), `python-dotenv`, `fastapi`/`uvicorn` (веб-форма).
  Модели данных — обычные `dataclass`. Без баз данных, очередей и фреймворков агентов.
- **Ошибки API** (неверный ключ, нет модели, лимиты, таймаут, обрыв соединения, пустой ответ)
  превращаются в понятные сообщения с причиной. На сетевые сбои и лимиты делаются повторы с паузой.
- **Некорректный вход** (битый JSON, нет `name`, не-объект, пустой ввод) даёт объяснение с номером строки;
  пустые значения характеристик попадают в отчёт.
- **Статус результата** (`ok`, `needs_review`, `insufficient_data`) и код выхода CLI позволяют встроить
  сервис в скрипт.
- **Вывод для контент-менеджера:** Markdown (копируется в CMS), JSON (для автоматизации); в начале —
  статус и длины заголовка и описания, в конце — раздел «Что проверить перед публикацией».

## 6. Ограничения

- **Проверка слов приблизительная.** Список «опасных» слов закрывает главные риски (сертификаты,
  стандарты, гарантии, превосходные степени), но не любую выдумку. Статус «ok» не заменяет вычитку
  человеком (так и написано в результате).
- **Числа в словесной форме** («два канала») проверкой чисел не проверяются.
- **Группы характеристик определяются по ключевым словам** в названии параметра. Нестандартные
  названия попадут в «Остальные характеристики из источника». Значение из описания берётся только по
  дословной цитате; если модель цитирует неточно, значение отбрасывается, и в таблице остаётся «данных нет».
  Значения из названия модели (например, «ДИ0,6») в таблицу не извлекаются.
- **Группы «Диапазон измерений» и «Точность» показываются всегда**, в том числе для приборов, у которых
  они не применимы (счётчик импульсов): там «данных нет».
- **Скудные данные.** Требование 800–1200 символов при двух-трёх фактах невыполнимо без «воды». Сервис
  делает текст минимальным и без рекламы, но он всё равно получается общим (см. демо). В реальной работе
  лучше доуточнить данные, чем публиковать такой текст.
- **Частотность запросов не измеряется** (нет доступа к Вордстату), запросы строятся по общим знаниям
  модели о том, как называют тип прибора.
- **Данные со страниц магазина неоднородны:** таблицы характеристик бывают многоколоночными, на некоторых
  страницах таблица и описание противоречат друг другу. Скрипт `fetch_product.py` переносит данные как
  есть и убирает только очевидный мусор (шапки таблиц, подписи к чертежам). Для страниц с семейством
  модификаций таблица описывает всё семейство.
- Время ответа 10–60 секунд (зависит от модели и сети). Прототип не хранит историю, не имеет авторизации
  и не рассчитан на параллельную нагрузку.

## 7. Что можно улучшить дальше

1. **Реальная частотность запросов.** Сейчас запросы строятся по общим знаниям модели о том, как называют тип
   прибора, но не по статистике. Варианты (по возрастанию усилий):
   - *Яндекс.Подсказки* (публичное автодополнение): бесплатно, показывает, что люди реально вводят после
     «датчик давления ОВЕН…». Сервис получает список подсказок и передаёт его модели как кандидатов, а модель выбирает
     подходящие. Частоты в цифрах нет, только порядок. Риск: внешний сервис может не ответить или ограничить запросы.
   - *Яндекс.Вордстат* (или Google Keyword Planner): настоящая частотность, но нужен кабинет и ключ API.
   - *Данные самого магазина* (Яндекс.Метрика, Search Console): лучший источник, показывает, как ищут именно этот
     магазин. Для их использования нужен доступ к статистике.
   В любом из вариантов в промпт добавляется список «топ-запросов» для типа прибора, а проверка кодом остаётся той же.
2. Просить модель указывать источник для каждого утверждения (цитата) и проверять, что цитата есть в данных.
3. Разбор многомодельных таблиц по модификациям и выбор строки для конкретного артикула.
4. Извлечение значений из названия модели (расшифровка кода «ПД100-ДИ0,6-115»), если у производителя есть открытая расшифровка в данных.
5. Пакетная обработка по фиду YML и выгрузка в CSV/XLSX для импорта в CMS.
6. Набор оценочных кейсов: прогон на 50–100 товарах, доля карточек со статусом `needs_review`, сравнение
   моделей и версий промпта по качеству и стоимости.
7. Кэш ответов по хешу входных данных, учёт стоимости запросов.
8. Проверка уникальности текста и SEO-метрик (плотность ключей, читаемость).
